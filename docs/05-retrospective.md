# 05 复盘与下一步

## 最难的问题

最难的不是串联四个工具，而是划清“模型可以决定什么”和“系统必须强制什么”。如果仅靠提示词要求模型不要越权，一次错误输出就可能把未确认的 19:00 保存为正式安排。因此本项目让模型负责选择动作，同时把审核通过、用户确认、幂等和最终状态校正放进确定性代码。

另一个容易遗漏的问题是重复请求。第一次保存后，同一时段会显示为已占用；如果不识别“被同一幂等请求占用”，第二次运行会错误地要求用户换时间。本实现增加 `reserved_by_same_request` 观察，再由保存工具返回原草稿。

## 学习收获

- Agent 的价值来自根据观察改变下一动作，而不是输出一段看似合理的决策日志。
- 提示词不能替代权限校验；关键业务边界必须由工具层执行。
- 失败状态也需要保留此前成功的审核和查询结果，便于恢复和排查。
- Trace 应记录可复核的动作、参数和结果，但不需要暴露模型内部思维过程。
- Mock 可以验证流程，却不能替代真实模型效果测试。

## 实际用时

2026-10-28 的 AI 辅助搭建、测试与文档整理约 30 分钟。候选人的代码复核、修改和真实模型验证尚未发生，相关用时应在提交前据实补充。

## 下一步

1. 使用目标模型复跑关键路径，检查是否会重复调用、提前结束或生成非法参数。
2. 为模型输出增加 JSON Schema 严格校验和一次可控的格式修复。
3. 将本地 JSON 草稿存储替换为带唯一约束的数据库事务。
4. 增加失败续跑：从已有 Trace 恢复已完成的审核和查询步骤。
5. 扩展时段模型，支持素材时长、频道容量、优先级、跨天和时区。
